前面几周你学的是"怎么让模型更强",这周学"怎么让模型不出事"。这不是写写原则就完事的软性话题,**它和前面的内容一样是工程问题:可以测量、可以写测试、可以改进。**

本周五个主题:

1. **公平性与偏见**:模型是否对不同人群区别对待
2. **可解释性**:模型为什么这样判断
3. **隐私**:数据和模型会泄露什么
4. **安全**:对抗样本、提示词注入
5. **幻觉与可靠性**:模型一本正经地胡说怎么办

## 第一部分:公平性与偏见

### 偏见从哪里来

|来源|例子|
|---|---|
|**历史偏见**|历史上的录用记录本身就偏向某类人,模型照着学|
|**采样偏见**|训练数据里某群体样本很少,模型对他们表现更差|
|**测量偏见**|用"被逮捕次数"代替"犯罪次数",而执法力度本身不均匀|
|**代理特征**|删掉了性别,但邮编、毕业学校仍然隐含相关信息|
|**反馈循环**|模型推荐什么用户就看到什么,产生的新数据又强化了模型|

### 常用的公平性指标

对两个群体 A、B,模型预测为"通过"的情况:

|指标|要求|含义|
|---|---|---|
|**人口统计均等**|两组被选中的比例相同|不看真实资质,只看结果比例|
|**机会均等**|两组中**真正合格**的人被选中的比例相同(TPR 相同)|合格的人不应因组别吃亏|
|**均等几率**|TPR 和 FPR 都相同|比机会均等更严格|

**重要的理论结论:** 当两组的真实基础比例不同时,这几个指标(加上"预测概率校准")**通常无法同时满足**。所以"选哪个指标"是**价值判断,不是技术问题**,需要业务方、法务、受影响群体一起讨论。


## 第二部分:可解释性

### 为什么需要

- **调试:** 模型判断依据是否合理,有没有靠"捷径"
- **信任与合规:** 贷款被拒、简历被筛,当事人有权问为什么
- **发现偏见:** 看看模型是否依赖了不该依赖的信息

### 捷径学习(shortcut learning)

模型会抓住训练数据里**碰巧相关**的特征,而不是真正的因果特征。经典案例:

- 医学影像模型把"拍片医院的标记"当作诊断依据,因为重症患者多去某些医院
- 图像分类器靠背景(雪地)而不是主体(哈士奇)来判断

准确率完全发现不了这类问题,**只有看模型"依据什么判断"才能发现**。


## 第三部分:隐私

### 风险有哪些

|环节|风险|
|---|---|
|**训练数据**|含个人信息,收集和使用是否有合法依据|
|**模型本身**|模型可能**记住**训练样本,被特定方式的提问还原出来(大模型尤其明显);攻击者还可以判断"某条数据是否在训练集里"(成员推断)|
|**服务日志**|用户输入原样存在日志里,日志泄露等于数据泄露|
|**RAG 系统**|检索时没做权限控制,A 部门员工问出了 B 部门的机密|
|**发给第三方 API 的内容**|把含个人信息的文本直接发给外部服务|


## 第四部分:安全

### 4.1 对抗样本:肉眼看不出来的"攻击"

给一张图加上**人眼几乎察觉不到**的微小扰动,就能让模型以很高的置信度分类错误。

**FGSM 的原理:** 第4周你学过,梯度告诉你"怎样调整参数让损失下降"。攻击者反过来,**对输入求梯度,朝着让损失上升的方向微调像素**:

```
x_adv = x + ε · sign(∂loss/∂x)
```

**现实意义:** 对抗样本在现实里有对应的场景,比如针对图像识别系统的物理世界干扰、对垃圾邮件和内容审核模型的规避。如果你的模型的判断结果会触发有价值的动作(放行、转账、封号),就要把"有人故意欺骗它"纳入威胁模型。

### 4.2 提示词注入:给第17、19周的系统做安全测试

第19周你已经见过一次。这里把它变成**可重复运行的测试**,用 canary(金丝雀)词检测:攻击成功就会在输出里出现这个独特标记。

### 4.3 其他要知道的攻击面

|攻击|说明|基本防御|
|---|---|---|
|**数据投毒**|在训练数据或 RAG 知识库里混入恶意样本|数据来源审核、异常检测、限制谁能写入知识库|
|**模型窃取**|通过大量查询 API 来复制你的模型|限流、监控异常查询模式|
|**成员推断/记忆提取**|判断某条数据是否被训练过|差分隐私、去重训练数据、限制输出|
|**供应链**|下载来源不明的模型或依赖,里面藏有恶意代码|只用可信来源、优先 `safetensors` 格式、锁定依赖版本|

## 第五部分:幻觉与可靠性

### 为什么会幻觉

模型的训练目标是"生成**看起来合理**的下一个词",不是"生成**真实**的内容"。第15周你亲手看过:每一步它只是在词表上输出一个概率分布并采样。**流畅度和真实性是两回事**,模型被问到不知道的东西时,最"合理"的续写往往就是编一个听起来像样的答案。

### 降低幻觉的实用手段

|手段|做法|效果与注意|
|---|---|---|
|**接地(RAG)**|第17周:先检索再回答,要求只依据资料|效果最显著,但检索错了照样错|
|**允许拒答**|明确告诉模型"不知道就说不知道"并设阈值|上面的实验可以看到差别|
|**要求引用**|每个结论标注出处,**程序校验引文真的存在于资料里**|模型也可能伪造引文,所以必须程序校验|
|**事后核查**|让第二次调用检查答案与资料是否一致|增加成本,可作为高风险场景的把关|
|**限制范围**|只让模型回答它被设计覆盖的领域|范围越窄越可靠|
|**人工把关**|高风险输出(医疗、法律、金融)必须经人确认|无法替代的最后防线|

**不要把模型"说话的语气自信"当作"答案可靠"的信号**,模型编造时的语气和说真话时一样笃定。


## 第六部分:把伦理变成工程流程

### 上线前检查清单

```
□ 用途:这个系统在做什么决定?出错的后果是什么?谁会受影响?
□ 数据:数据来源合法吗?有无个人信息?是否做了最小化和脱敏?
□ 偏见:按关键人群拆分评估过吗?差距在可接受范围内吗?(第一部分)
□ 解释:能说明主要判断依据吗?有没有靠捷径?(第二部分)
□ 隐私:日志存了什么?保留多久?谁能访问?(第三部分)
□ 安全:做过对抗/注入测试吗?最坏情况的权限边界在哪?(第四部分)
□ 可靠性:幻觉率测过吗?高风险输出有人工把关吗?(第五部分)
□ 监控:上线后怎么发现问题?漂移监控就位了吗?(第21周)
□ 回滚与申诉:出问题能快速回滚吗?受影响的人有申诉渠道吗?
□ 责任:出了事谁负责?有事故响应流程吗?
```

### 红队测试(Red Teaming)

**让一批人专门以"攻击者"的身份找系统的漏洞**:诱导它输出不当内容、绕过限制、泄露信息、对某些人群表现更差。发现的问题整理成测试用例,加入前面几部分的回归测试集。**测试者最好包含不同背景的人**,因为开发者往往想不到别人会怎样误用或被伤害。
